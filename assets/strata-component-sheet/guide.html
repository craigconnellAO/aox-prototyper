01

What is design.md?

A single text file (~3,400 lines) that contains every rule, colour, font, icon, and component definition from the AO design system — written so AI tools can read it and produce on-brand prototypes automatically.

Think of it as a recipe book

Just like a recipe book tells a chef which ingredients to use and how to combine them, design.md tells an AI tool exactly what colours, fonts, spacing, and components make something "look like AO."

Without it, the AI guesses — and guesses wrong. With it, every output is consistent and on-brand from the first prompt.

What it isn't

It's not a component library you install. It's not code that runs on ao.com. It's not a replacement for Strata. It's a reference document — a cheat sheet that removes guesswork from AI-generated prototypes.

How you use it

Attach the file to your AI session (Claude, ChatGPT, Figma Make, Cursor, Kiro). Then prompt normally. The AI cross-references the file for every decision — colours, fonts, spacing, components — and runs a quality checklist before showing you the result.

02

The intro & rules section

The opening of design.md sets the ground rules for what every AI output should look like. Three parts: format rules, a starter template, and a quality checklist.

Output Format Rules

These tell the AI: "every prototype must be a single HTML file, must work on mobile first, must load our icon font, and must not call external services." Keeps outputs simple, self-contained, and safe to share.

Quick-Start Boilerplate

A template skeleton the AI copies as its starting point — like a blank form with the right letterhead already printed.

Pre-flight Checklist

A final quality check the AI runs before showing you the result. Verifies things like "are all colours using tokens?" and "are icons done properly?"

Like a pilot's pre-flight checklist — the AI checks every critical item before takeoff.

Example: Pre-flight checklist items

  • Does the <head> include the Strata icons stylesheet?
  • Are all colours using var(--token-name), never raw #hex?
  • Do all icons use <i class="ico ico-{name}">, not emoji?
  • Does every component carry its data-aods attribute?
  • Is the layout mobile-first?
### Output Format Rules

Every generated prototype must follow these rules:

- **Single self-contained HTML file** with an inline <style> block
- **Mobile-first layout** with breakpoints: sm: 544px, md: 768px, lg: 990px, xl: 1200px
- **Strata icons stylesheet** must be included in <head>
- **<script> is permitted** for lightweight prototype interactions only

---

### Pre-flight Checklist

Before returning output, verify every point:

- [ ] <head> includes the Strata icons stylesheet link
- [ ] <style> contains the SmileyFace @font-face declarations
- [ ] <style> contains the full :root token block — no raw hex values
- [ ] All colours reference a CSS custom property — var(--token-name)
- [ ] All icons use <i class="ico ico-{name}" aria-hidden="true">
- [ ] Every component root carries its data-aods="{name}" attribute
- [ ] Layout is mobile-first

Tokens — colours & spacing

"Tokens" are named values. Instead of saying "use #00893e", we say "use action-primary-base." Change it in one place and it updates everywhere. This is the largest section of the file.

Primitives (the raw palette)

The base colour swatches: 10 shades of grey, the brand greens, and the decorative "food palette" (named things like toast, steam, jam). These are the paint pots on the shelf.

Action tokens (things you tap)

Colours for interactive elements. Green for the main call-to-action, blue for secondary actions, grey for disabled. Each has hover, active, and focus states built in.

UI Surface tokens (meaning through colour)

Backgrounds that communicate: blue-tinted for "info/selected," green for "success," amber for "warning," red for "error." Each surface has pre-tested readable text colours.

Like traffic lights — green means success, amber means caution, red means error. These tokens work the same way for screen backgrounds.

Spacing & radius

A fixed set of gap sizes (multiples of 4px) and corner roundness values. No in-between values allowed — this keeps visual rhythm consistent.

Typography — fonts & text sizes

AO uses two fonts with strict job assignments. Getting this wrong is one of the most visible brand inconsistencies.

SmileyFace — the brand font

Used for all headings, display text, and every button label. It's what makes AO look like AO. Key rule: never goes below 14px.

Inter — the workhorse font

Clean and highly readable. Used for body paragraphs, form labels, helper text, captions — everything that isn't a heading or a button.

The type scale

A fixed ladder of text sizes. The AI picks from this ladder — it never invents a new size.

Like shirt sizes (XS, S, M, L, XL) — you pick the one that fits, you don't ask for "medium-and-a-half."

### AO Typography

Two typefaces, strict role separation. Never swap them.

| Family      | Role                                                    |
|-------------|---------------------------------------------------------|
| SmileyFace  | Headings, display text, and all button labels (CTAs).   |
| Inter       | All body text, UI labels, helper copy, form fields.     |

#### Type scale

| Class                | Font             | Size         | Use                      |
|----------------------|------------------|--------------|--------------------------|
| text-display-headline| SmileyFace-Headline | 2.5rem (40px) | Hero headlines         |
| text-display-lg      | SmileyFace 700   | 2rem (32px)  | Large section headings   |
| text-display         | SmileyFace 700   | 1.5rem (24px)| Standard page headings   |
| text-title           | SmileyFace 700   | 1rem (16px)  | Subsection headings      |
| text-cta             | SmileyFace 700   | 1rem (16px)  | All button labels        |
| text-body            | Inter 400        | 1rem (16px)  | Default body copy        |
| text-body-sm         | Inter 400        | 0.875rem     | Supporting copy          |
| text-caption         | Inter 400        | 0.75rem      | Captions, metadata       |

#### Typography rules

- SmileyFace minimum size: 14px (0.875rem). Below that, use Inter.
- Body line-length: max 65–75 characters.
- Links: always Inter Bold, never underlined by default.
05

Icons — pictograms & symbols

AO uses a custom icon font called Strata, loaded from AO's CDN. The file catalogues every available icon and explicitly forbids emoji or Unicode symbols.

How they work

To show an icon, you reference its name (like "ico-basket" or "ico-delivery"). No image files needed — they scale with text and inherit colour from their parent.

Why no emoji?

Emoji look different on every device. A tick on iPhone looks nothing like one on Windows. Strata icons look identical everywhere.

Accessibility

Decorative icons (next to text) are hidden from screen readers. Icon-only buttons must have a text label for assistive technology.

### AO Icon System — Strata Icons

#### Usage

Icons use an <i> element with two classes: the base `ico` class plus the icon name.

```html
<i class="ico ico-basket" aria-hidden="true"></i>
```

##### Accessibility

- Decorative icons (paired with visible text): add aria-hidden="true"
- Meaningful icons (icon-only buttons): add aria-label on the parent button

#### Sizes

| Class  | Scale   | Use                    |
|--------|---------|------------------------|
| ico-sm | 0.875em | Inline with body text  |
| ico-md | 1em     | Standard UI icons      |
| ico-lg | 1.25em  | Nav icons, card icons  |
| ico-2x | 2em     | Hero features          |
| ico-3x | 3em     | Empty states           |

#### Rules

- Never use emoji (✓ ✕ 🛒) — always Strata icon classes
- Icons inherit colour from their parent element
- Icon-only buttons require an aria-label

Components — the building blocks

The longest section (~1,600 lines). It defines 16 reusable UI elements — each with its exact structure, styling, allowed variants, and usage rules. Think of them as LEGO bricks you snap together to build pages.

What each blueprint contains

Every component has: a description of what it is, its allowed variants, the HTML markup, the CSS styling, and rules for when/how to use it. The AI copies these blueprints exactly — it doesn't improvise.

The 16 components

  1. Button — primary, secondary, tertiary, dark, white, inactive
  2. Field / Input — text inputs with labels & validation
  3. Select — styled dropdown menus
  4. Textarea — multi-line text inputs
  5. Checkbox / Radio — card-style selection controls
  6. Tag — coloured pill badges (In stock, New, etc.)
  7. Notice — feedback banners (info, warning, success, error)
  8. Card — content surface with state variants
  9. Breadcrumb — "you are here" navigation
  10. Tabs — content switcher
  11. Accordion — collapsible sections
  12. Quantity stepper — +/- amount control
  13. Loading spinner — CSS ring + branded AO loader
  14. Nav (Header) — site header in 4 variants
  15. Footer — site-wide footer
  16. Switch24 — payment option selectors

Example: Button component (what the AI produces)

SmileyFace Bold label · 8px radius · 1px border · green = main CTA, blue = secondary, grey = tertiary. Only one green button per section.

#### 1 · Button

8px radius, SmileyFace Bold label, 1px border.
The `primary` variant is reserved for the one main CTA per visual section.

Variants: primary (green) · secondary (blue, outlined) · tertiary (neutral)
          · white (on dark) · dark (alt primary) · inactive (disabled)

Sizes: default · btn-lg · btn-sm · btn-icon (square) · btn-full (100% width)

##### HTML

```html
<button class="btn btn-primary" data-aods="button">Add to basket</button>
<button class="btn btn-secondary" data-aods="button">View details</button>
<button class="btn btn-tertiary" data-aods="button">Compare</button>
```

##### CSS

```css
.btn {
  display: inline-flex; align-items: center; gap: 0.5rem;
  padding: 0.875rem 1.5rem; border-radius: var(--radius-sm);
  font-family: 'SmileyFace', Georgia, serif; font-weight: 700;
  font-size: 1rem; line-height: 1; border: 1px solid transparent;
  cursor: pointer; transition: background 150ms;
}
.btn-primary {
  background: var(--action-primary-base);
  color: var(--action-primary-contrast);
}
```

Patterns — full page recipes

While components are individual bricks, patterns show how to assemble them into complete pages. This section contains 10 page-level recipes.

What's covered

Sign in, form validation, product detail pages, basket summaries, modals, empty states, order confirmations, category listings, account dashboards, and the full multi-step checkout flow.

Header selection guide

A decision tree: which header variant goes with which page type. Stops the AI from putting a search bar on a payment screen or a full nav on a checkout page.

What each pattern defines

The overall page grid, which components go where, spacing between sections, and how layout adapts from mobile to desktop. It's the floor plan for each room type.

If components are ingredients, patterns are complete recipes — "to make a checkout page, combine these components in this order with this layout."

Anti-patterns — the guardrails

The final section is a list of common mistakes AI tools make, with explicit "refuse and replace" instructions. It's the most important section for preventing brand drift.

How it works

Each rule follows a pattern: Match (spot the mistake) → Refuse (don't produce it) → Replace (use the correct alternative). The AI checks its own output against these rules before showing you anything.

Categories covered

Colour & tokens, component variants, typography, layout & hierarchy, CTA copy, accessibility, surfaces & shadows, spacing, and imagery. Every common drift point is explicitly addressed.

Example: Anti-pattern rules in action

### AO Anti-patterns — Refuse and Replace

If a request or generated output would force any of the below,
stop and use the listed AO-correct alternative.

The pattern: Match → Refuse → Replace.

#### Colour & tokens

| ❌ Don't                        | ✅ Do                                    |
|---------------------------------|------------------------------------------|
| background: #00893e;            | background: var(--action-primary-base);  |
| color: #011f44;                 | color: var(--type-primary);              |
| Use palette-heat for an error   | Use ui-error tokens                      |

#### Typography

| ❌ Don't                        | ✅ Do                                    |
|---------------------------------|------------------------------------------|
| Inter on a button label         | Always SmileyFace Bold on buttons        |
| SmileyFace at 12px              | Minimum is 14px; below that use Inter    |
| ALL CAPS on buttons or tags     | Sentence case                            |

#### Component variants

| ❌ Don't                        | ✅ Do                                    |
|---------------------------------|------------------------------------------|
| Button variant="success"        | Only: primary, secondary, tertiary, etc. |
| Tag color="purple"              | Tags only use ui-* groups                |
